# Сотрудники и авторство

Локальная инфраструктура с реальными профилями Романа Сергеева и Дамира Вахитова.
Распределение 30 статей: Роман — 17, Дамир — 13. Явная карта находится в
`data-import/article-authors-20260922.json`, профили — `data-import/experts-20260922.json`.
Скрипт `scripts/apply-experts-20260922.mjs` делает backup и атомарный перенос один раз;
повторные запуски не меняют редакторские правки. Уже назначенные авторы сохраняются.
Фото копируются без изменения оригиналов в отслеживаемую папку public/employees.
Внешние интервью используют relation=about и Article.about, а не Article.author.

- Админка: `/panel-rg7x/employees`. Имя, slug, должность, фото, описание, био,
  экспертиза, подтверждённые квалификации, личные профили, внешние авторские публикации, SEO.
- Профиль по умолчанию скрыт. Для публикации нужны имя, должность, фото и описание.
- Публичные адреса `/сотрудники` и `/сотрудники/<slug>`; черновики возвращают 404.
  Пустой список имеет noindex и не попадает в sitemap. Никаких демопрофилей в БД.
- В статье выбирается один фактический автор через `authorId` (постоянный ID сотрудника).
  До предоставления реальных данных поле необязательное; старые статьи остаются без
  персональной подписи. Обязательность новых авторов включать после разбора старых
  импортов и назначения сотрудников, чтобы сейчас не блокировать редакцию.
- Профиль получает все статьи по ID, а статья — подпись и ссылку на опубликованный профиль.
- Черновой/снятый профиль не раскрывается через статью; связанного сотрудника нельзя удалить.
- JSON-LD: ProfilePage.mainEntity → Person; Article.author → тот же Person @id.
  Внешние публикации — Article в hasPart профиля, а не sameAs сотрудника.
  sameAs — только личные профили. hasCredential — квалификации/удостоверения,
  не произвольные рекламные достижения. Не добавлять выдуманный стаж или награды.
- Старые Article/BlogPosting в произвольном seo.jsonLd убираются при рендере,
  чтобы не выдавать противоречащих авторов. Другие типы разметки сохраняются.
- Для старых XLSX ничего менять не нужно. Необязательные колонки `authorId`
  (или `ID автора`) и `authorSlug` (или `Slug автора`) листа СТАТЬИ привязывают автора.
  Пустые ячейки сохраняют связь; неизвестный автор пропускает строку с предупреждением.
  Для снятия автора использовать админку. ID имеет приоритет над slug.
- Скрипты старого деплоя, не передающие authorId, сохраняют существующую связь.
- Профили SSR: правки доступны сразу. Статьи ISR: админские правки инвалидируют
  реальные вложенные URL, включая статьи при изменении сотрудника.
- Миграция добавляет employees и nullable posts.authorId, не переименовывает существующие
  поля и URL. Перед будущим продакшен-деплоем сделать консистентный backup SQLite.
- Проверки: `node --test tests/employee-authorship.test.mjs`, `npm run build`.
- Установка MCP/SEO инструментов приостановлена по просьбе пользователя.

Проверено локально 2026-09-22: production build, тест миграции/импорта/связей,
HTTP 200 профиля/списка/статьи/sitemap; неизвестный профиль 404, admin API без
сессии 401. В браузере проверены профиль и переходы статья → автор → статьи,
десктоп и 390px. Данные проверки лежат в отдельной gitignored тестовой БД.

прямой /team перенаправляется на канонический /сотрудники.
